# NIP-333: Bitcoin Block Headers

`draft` `optional`

This NIP defines a protocol for distributing Bitcoin block headers over Nostr.

## Abstract

Bitcoin block headers are 80-byte cryptographic proofs. This specification defines a minimal, self-contained event for publishing the latest 12 headers via Nostr. The event includes URLs to additional data sources, enabling clients to bootstrap and sync the full header chain.

## Event Format

### Kind

```
33333
```

A **parameterized replaceable event** (30000-39999 range). Relays store only the latest version for each `(pubkey, kind, d-tag)` combination. The `d` tag is the network code, so each network is its own replaceable stream — one publisher key can serve several networks without overwriting itself.

### Tags

| Tag | Required | Description |
|-----|----------|-------------|
| `d` | Yes | Network stream identifier (see [Networks](#networks)) — MUST equal the `n` tag |
| `n` | Yes | Network code (see [Networks](#networks)) |
| `tip` | Recommended | Chain tip height (last header in content) |
| `u` | Recommended | Data source URL |
| `p` | Optional | Other trusted publisher pubkey |
| `alt` | Recommended | Human-readable description per [NIP-31](31.md) |

Note: `tip` is recommended but optional — clients can derive height from header chain validation.

**Legacy `d: latest`:** earlier drafts of this NIP used `d: latest` for all networks. Because relays replace on `(pubkey, kind, d)`, a single key publishing two networks would overwrite its own stream. During migration clients MAY query `"#d": ["btc", "latest"]` and keep the newest verified event.

### Networks

| Value | Network | Header | Proof-of-work hash |
|-------|---------|--------|--------------------|
| `btc` | Bitcoin mainnet | 80 bytes | SHA256d |
| `tbtc3` | Testnet3 | 80 bytes | SHA256d |
| `tbtc4` | Testnet4 | 80 bytes | SHA256d |
| `btcb2` | Bitcoin Knots BLAKE2b chain (mainnet, forked at height 961,640) | 164 bytes | BLAKE2b (Knots v2 header) |
| `tbtc4b2` | Bitcoin Knots BLAKE2b chain on testnet4 (forked at height 150,308) | 164 bytes | BLAKE2b (Knots v2 header) |

The header length and proof-of-work hash are properties of the network; every header in a stream has the network's length. A network code is the base chain's code plus an algorithm suffix (`b2` for BLAKE2b); testnets keep their number.

### Content

Exactly **12 concatenated block headers** of the network's header length, encoded as lowercase hexadecimal:

```
length = 12 headers × header bytes × 2
       = 1,920 characters for 80-byte networks (btc, tbtc3, tbtc4)
       = 3,936 characters for 164-byte networks (btcb2, tbtc4b2)
```

Headers in ascending order. The 12th header is the chain tip. First header height = tip - 11.

## Data Sources

The `u` tag points to header archive files. Two files provide complete coverage:

| File | Contents |
|------|----------|
| `{network}.archive.bin` | All completed epochs (immutable, grows each epoch) |
| `{network}.current.bin` | Current epoch in progress (up to 2016 headers) |

The NIP-333 event itself provides the chain tip (latest 12 headers).

### URL Schemes

The `u` tag accepts standard URL schemes:

- `https://` — Remote HTTP(S) resources
- `file://` — Local filesystem paths

Clients SHOULD try URLs in tag order, preferring faster sources. Common local paths include `~/.spv/{network}.archive.bin` and `~/.spv/{network}.current.bin` for offline operation and reduced bandwidth usage.

### Sync Strategy

```
1. Subscribe to kind:33333 → get tip (12 headers)
         ↓
2. GET btc.current.bin → current epoch
         ↓
3. GET btc.archive.bin → completed epochs (background)
         ↓
4. Stay subscribed for new blocks
```

Clients validate that headers chain together. If a gap exists between `current.bin` and the nostr tip, refetch `current.bin`.

## Discovery

- **`u` tags** — Data source URLs (preferred, follow-your-nose)
- **`p` tags** — Other trusted publishers
- **`did:nostr`** — Optional identity via [did:nostr](https://nostrcg.github.io/did-nostr/)

## Header Structure

### 80-byte header (`btc`, `tbtc3`, `tbtc4`)

| Field | Bytes | Offset | Description |
|-------|-------|--------|-------------|
| Version | 4 | 0 | Block version (little-endian) |
| Previous Hash | 32 | 4 | Hash of previous block |
| Merkle Root | 32 | 36 | Transaction merkle root |
| Timestamp | 4 | 68 | Unix timestamp |
| Bits | 4 | 72 | Difficulty target (compact) |
| Nonce | 4 | 76 | Proof-of-work nonce |

### 164-byte header (`btcb2`, `tbtc4b2`)

Bitcoin Knots' v2 header (v29.4.1, `primitives/block.h`). The first 80 bytes keep the layout above, with bit 31 of the version set to mark v2 and the timestamp possibly offset (see flags). Then:

| Field | Bytes | Offset | Description |
|-------|-------|--------|-------------|
| Nonce2 | 4 | 80 | Second proof-of-work nonce |
| Nonce3 | 4 | 84 | Third proof-of-work nonce |
| Extranonce | 16 | 88 | 128-bit extranonce |
| Time offset | 4 | 104 | Added to the wire timestamp when flags bit 2 is set |
| Tx count | 2 | 108 | Number of transactions in the block (committed) |
| Flags | 1 | 110 | Bits 0-1: ASIC layout profile; bit 2: time offset in use; bits 6-7 reserved |
| XOR mask clear bits | 1 | 111 | High bits of the proof-of-work XOR mask that are cleared |
| XOR key | 16 | 112 | 128-bit proof-of-work XOR key |
| Height | 4 | 128 | Block height (committed, signed little-endian) |
| Merge-mining slot | 32 | 132 | Reserved (all zeros so far) |

The block hash of a v2 header is **not** SHA256d of these bytes: it is a tagged-SHA256 commitment over the fields, then two BLAKE2b-256 passes over a profile-dependent layout, XORed with a key-derived mask. Clients on these networks MUST use that construction for the proof-of-work check; see [Implementation](#computing-header-hash).

## Subscription

```json
["REQ", "headers", {
  "kinds": [33333],
  "authors": ["cccccccc829b802b7bf52d43edf7cfe62ac89f332a318b6826ac8bd6e73660da"],
  "#d": ["btc"],
  "limit": 1
}]
```

## Verification

Clients SHOULD verify:

1. **Signature** — Event signed by trusted pubkey
2. **Length** — Exactly 12 headers of the network's length (1,920 hex characters for 80-byte networks, 3,936 for 164-byte networks)
3. **Chain** — Each `prevHash` links to previous header's hash
4. **Proof-of-work** — Header hashes, computed with the network's hash function, meet difficulty targets

## Security Considerations

- **Trust**: Only subscribe to known, reputable publishers
- **Cross-reference**: Compare tips from multiple `p` tag publishers
- **Relay diversity**: Use multiple relays for redundancy
- **Source verification**: Validate data from `u` tag sources

## Implementation

### Parsing Headers

For an 80-byte network (`btc`, `tbtc3`, `tbtc4`); for a 164-byte network use `164` in place of `80` (`328` in place of `160`) and read the additional fields at the offsets above.

```javascript
function parseHeader(hex, index) {
  const offset = index * 160;
  const headerHex = hex.slice(offset, offset + 160);
  const bytes = new Uint8Array(80);
  for (let i = 0; i < 80; i++) {
    bytes[i] = parseInt(headerHex.slice(i * 2, i * 2 + 2), 16);
  }
  const view = new DataView(bytes.buffer);
  return {
    version: view.getUint32(0, true),
    prevHash: bytesToHex(bytes.slice(4, 36).reverse()),
    merkleRoot: bytesToHex(bytes.slice(36, 68).reverse()),
    timestamp: view.getUint32(68, true),
    bits: view.getUint32(72, true),
    nonce: view.getUint32(76, true)
  };
}
```

### Computing Header Hash

SHA256d, for the 80-byte networks:

```javascript
async function computeHeaderHash(headerHex) {
  const bytes = hexToBytes(headerHex);
  const hash1 = await crypto.subtle.digest('SHA-256', bytes);
  const hash2 = await crypto.subtle.digest('SHA-256', hash1);
  return bytesToHex(new Uint8Array(hash2).reverse());
}
```

For `btcb2` and `tbtc4b2` the hash is Bitcoin Knots' BLAKE2b construction, too long to inline here. Reference implementations, verified against Knots' own test vectors and live blocks: [bitcoin-desktop/schema](https://github.com/bitcoin-desktop/schema) (`codec/pow/knots-header-v2.js`, used with the `knots-blake2b` overlay) and Bitcoin Knots itself (`src/primitives/block.cpp`, `CBlockHeader::GetHash`).
